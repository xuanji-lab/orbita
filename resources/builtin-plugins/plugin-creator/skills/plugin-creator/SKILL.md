# 做插件：边聊边把详情填出来

> 插件详情页就是清单 `.claude-plugin/plugin.json`：**每聊定一节，你把它写进清单对应的字段，右栏的详情长页几秒内自己长出那一节**——界面不用你操心，你只管把清单填对、把卡做好。
> 顺序是活的但内容有先后：需求和那些技能、输入输出、工作流都确定了以后，才到看板卡片（用户想先聊卡片就先做卡片）。最容易走偏的两件事：一上来就写脚本爬数据；或者把卡片做成不属于这张卡的东西——外框、圆角是 Orbita 的，你只做卡里面。

## 语言（先看这一条）

**用用户自己写的文字的语言回复**：他用中文写需求你就回中文，用英文你就回英文。你收到的消息里有一段英文系统包装（`<mentioned_tools>`、"The user explicitly invoked…"、`/skill:` 这类），那不是用户写的，**别被它带成英文**。分不清时看他亲手打的最后一段字（预填的那一句也算）。你对他说的话、卡片上的字、`spec.md`、`plugin.json` 的 description 都用这个语言。

## 先认路

这个技能所在的文件夹 = 本 SKILL.md 所在的目录（下文记作 `<本技能>`）。里面有：

| 位置 | 什么时候读 |
|---|---|
| `<本技能>/references/plugin-layout.md` | **填清单任何一节之前必读**：目录、plugin.json 全部字段（workflow 的 `wait`、`io`、`external`、`board`、`tuned`）、路径变量、上限、常见坑 |
| `<本技能>/references/skill-writing.md` | 第 5 步写插件里的技能（SKILL.md）之前读，几分钟 |
| `<本技能>/assets/plugin-skeleton/` | 第 2 步用的骨架：最小清单（只有名字、需求、`tuned: false`）+ taste.md |
| `<本技能>/assets/skill-skeleton/` | 第 5 步才用：一条示例技能 + 示例脚本 |
| `../find-existing/SKILL.md` | 第 2 步「主动找现成的」：按它做 |
| `../board-style/SKILL.md` | 第 4 步做看板卡片：四档尺寸、卡模板骨架与规矩；用户要换风格的子流程也在它里面 |

工具：`list_plugins`（先看已有的）、`preview_plugin`（第 2 步让右栏出现「正在做」，**调一次就够**）、`install_plugin`（第 6 步）、`create_skill`（**不用它**：插件里的技能直接写在插件文件夹里）、浏览器工具。

## 流程（七步）

**停与不停**——这是这个流程里最容易走偏的地方：

- **停下来等用户**：第 4 步第一张卡摆出来之后（他说「可以」才做下一张）；改完卡上某一处之后；第 6 步装之前问一句。
- **不停，一口气往下做**：第 1 步写 `intent.md`（贴给他看一下就继续，他不吭声就是通过）；第 2 步找现成的（一句话说出你的决定就继续，只有真有取舍才停）；第 5 步写技能、脚本、试跑、批量。
- 每写完清单一节，右栏自己长出那一节；用一两句话告诉他「右栏现在多了什么」，别写长报告。

### 1. 听需求，写下需求这一节

用户已经说清楚的别再问。缺关键信息才问，最多 2 个：它每次要产出什么？他最后看什么？

然后在 `<工作区根>/plugins/<名字>/` 的 `intent.md` 里写几行（名字规则见 layout 参考）：

```markdown
# 意图
一句话：给谁、做什么、产出什么。

# 验收清单（参照，不是闸门）
- 看到 X 就算对。写 3–5 条，每条能检查。
```

贴给他看（短），**不用等回复**。需求同一句话写进清单的 `description`（它会显示在插件列表里，写人话）。

### 2. 主动找现成的，搭骨架，让右栏出现「正在做」

动手写之前按 `../find-existing/SKILL.md` 找一遍，先调 `list_plugins` 看这个工作区里是不是已经有类似的。

- 用户的需求里**点名了底子**（「在 X 的基础上做」「用我那个 Y 技能」）：直接用，不用再找。
- 找完**只在有真取舍时停下来问**（要放弃他已有的方案、许可证受限、候选互斥）；没有真取舍就**一句话说出你的决定**继续，不要在两个不冲突的候选之间硬停下问。

然后搭骨架：

```bash
mkdir -p "<工作区根>/plugins/<名字>"
cp -R "<本技能>/assets/plugin-skeleton/." "<工作区根>/plugins/<名字>/"
```

（第 1 步写的 `intent.md` 已在这个文件夹里，骨架不带它，不会被覆盖。）把骨架里的 `__…__` 占位全换掉（name、displayName、description、作者）。**只能写在 `<工作区根>/plugins/<名字>/` 里面。** 这一步**还不要**写技能、脚本，也**不要**做卡片。骨架写好就调一次：

```
preview_plugin({ path: "<工作区根>/plugins/<名字>" })
```

它**只扫描、不安装**，右栏出现「正在做 · 还没装」的详情长页：现在只有需求一节是实的，其余节画着虚线框「还没聊到」——那就是你们接下来要聊的东西。**调一次就够**——之后你每写进清单一节，右栏几秒内自己长出来，**别每改一次调一次**；他说右栏没出现再调。返回里有「要修的东西」就修（技能还没写、卡片还没做不算，先不管）。

### 3. 边聊边填：技能、输入与输出、要你填的、外接

顺序随意，用户想到哪聊到哪；**聊定一节写一节**，每写完告诉他右栏多了什么：

- **技能（`skills/`）**：这个插件要哪几条技能、各做什么。先在对话里列出来让他确认（「取数据一条、写摘要一条，够吗？」），文件第 5 步才写——技能的名字定了，清单的工作流就能点名它。
- **输入与输出（`orbita.io`）**：它读什么、写什么、多久一次，给人看：

  ```json
  "io": {
    "reads":  [ { "path": "intent.md", "note": "10 条选文理念" } ],
    "writes": [ { "path": "data/today.json", "note": "「今日一篇」这张卡读它", "when": "每天" } ]
  }
  ```

- **要你填的（`userConfig`）**：API key、目录这类要用户自己填的。密钥用 `sensitive: true`（进系统密钥库，不落盘），**不要把密钥写进清单默认值**。
- **外接（`orbita.external`）**：用到的外部服务 / 命令行，一条一行：

  ```json
  "external": [ { "name": "Semantic Scholar API", "kind": "api", "account": false, "resident": false, "note": "只在跑的时候联网" } ]
  ```

### 4. 工作流，和看板卡片

**工作流（`orbita.workflow`）**：把做事的步骤列出来（给人看，不执行，一般 4–8 步，写「人眼里的步骤」）。列完**问一句**：「哪几步要你拍板？」

- 在**看板上点**的（比如卡上有「有用 / 不相关」按钮）写 `"wait": "board"`；
- 在**对话里说**的写 `"wait": "chat"`；
- 自动往下跑的步骤不写 `wait`。

```json
"workflow": [
  { "title": "取今天的新论文", "skill": "lit-fetch", "detail": "cs.CL 前 5 篇" },
  { "title": "每篇写一句话摘要", "skill": "lit-summarize" },
  { "title": "你标记哪篇有用", "skill": "lit-fetch", "wait": "board" },
  { "title": "写进看板数据", "output": "data/today.json" }
]
```

详情页里等用户的步骤会带手形标「等你」。他说「都自动就行」就一个都不写。

**看板（`orbita.board`）**：先定**有哪几张卡、各几格**，再做**卡里**。规矩、模板骨架、换风格的子流程全在 `../board-style/SKILL.md`，这里只讲顺序：

1. 问他：这个插件跑完，你想看哪几张卡？**一张卡只说一件事**（「今日一篇」是一张，「本周汇总」是另一张）。卡只有四档尺寸：`1x1 / 2x1 / 1x2 / 2x2`（宽×高），先定每张几格。
2. 清单里写下 `cards`（每张：`id` 小写短横、`title`、`size`、`template`、`data`、`sample`），文件先空着：

   ```json
   "board": {
     "title": "文献追踪",
     "cards": [
       { "id": "today", "title": "今日一篇", "size": "1x1", "note": "标题 · 为什么挑它 · 相关 / 不相关",
         "template": "./board/today.html",
         "data": "${CLAUDE_PLUGIN_ROOT}/data/today.json",
         "sample": "./board/today.sample.json" }
     ]
   }
   ```

3. **先用样例磨定一张**：写这张卡的 `sample`（1 条真记录最好），拿 `../board-style/assets/board-template.html` 做卡里，右栏「看板样式」节就会出现这张卡（数据文件还不存在，用的是样例，卡外会标「样例」）。问他哪里想改。**停。**
4. 他说「可以」再做下一张，每张都这样单张磨；全部定稿后写 `plugins/<名字>/taste.md`（他选了什么、否决了什么、**原话逐字**、日期）。

这一步**不写脚本、不爬数据**。他对某张卡的整体风格不满意（「不是这种感觉」「太像 XX 了」）才换风格（board-style 的子流程，出 2 个方向）；局部意见（「字大一点」「这行去掉」）就地改，不要因此重新出方向。

### 5. 定稿之后：写技能和脚本，试跑，批量

按 `references/skill-writing.md` 写每条技能（description 要具体、「推」一点），骨架在 `<本技能>/assets/skill-skeleton/`，脚本放 `scripts/`。

- **脚本的输出 = 对应那张卡的 `data` 文件，形状与那张卡的 `sample` 一致**（字段名一一对应）。想加字段：先改 sample 和卡模板（回第 4 步和他说一声），再改脚本。
- **每条技能跑完，最后一步都调 `show_plugin_board({ plugin: "<插件名>" })`**：卡会出现在对话里。清单 `tuned` 初始是 `false`——工具会提醒你「用一两句说明做了什么，请用户挑错」，照做。
- **先试跑**：数据写进卡的 `data` 文件，右栏的卡自动从样例换成真数据（告诉他这一点），给他看 2–3 条真实记录（不是整个文件）。试跑只是看一眼：脚本跑得通、形状对、卡拿真数据好不好看；**不要**为了把验收清单全打勾反复改脚本再跑。做到了什么、没做到什么、没验证什么**如实**告诉他。
- 试跑通过（有产出、形状对）就**直接批量跑**，不用再问；量很大 / 要很久 / 要花钱（逐条调模型）才先说一声。
- 数据必须是真的。网络不通、接口变了就如实说，不要编造当产出；用样例预览要明说是样例。

**`tuned` 什么时候改**：用户说「以后不用解释了」，或连续几次看了卡没意见——**先问一句**「以后这个插件跑完就只出卡、不加说明，可以吗？」，他说可以才把清单里 `tuned` 改成 `true`，并告诉他这会改变什么（以后跑完只有一行加卡，不再解释）。

### 6. 装之前问一句，同意才装

做好后，**先在对话里用一句话问**：「做好了，可以装了吗？（会装进『<工作区名>』，只在这个工作区启用）」**然后停**，不要在同一轮里调用 `install_plugin`。他说可以（或类似的话）才调：

```
install_plugin({ path: "<工作区根>/plugins/<名字>" })
```

它**立即返回**，不等人。两种结果：

- **「Installed」**：已经装上了，对话里自动留了一行「已装上 X · [卸载]」。**别重复那一行的内容**。技能要到**下一轮**才加载，要试就让他新开一条对话，或你直接按它的 SKILL.md 做一次演示。
- **「Not installed yet」**：它带 MCP（会在本机启动程序）、或范围是所有工作区、或这条会话在 Manual 权限档，所以没装，对话里留了一行带 [安装] 的行。**这一轮到此结束**：用一句话告诉他那一行在等他点（什么时候点都行），**别复述那一行已经写出来的命令和原因、别重调、别催、别在文字里再问一遍**。

返回错误（清单不对、重名、路径越界）时，错误里写了怎么改，改完再调。他说「先别装」「再改改」就回第 4 步。

### 7. 问要不要定时跑

装好后问一句：「要不要让它每个工作日早上自己跑一次？」他说要，就建一条**指向这个插件**的自动化：

```
automation_create({ title: "文献追踪", prompt: "调用 lit-tracker 插件，跑完把看板显示出来。",
                    schedule: { "kind": "daily", "time": "09:00", "weekdays": [1,2,3,4,5] },
                    target: "new_session", plugin: { name: "lit-tracker" } })
```

自动化建好直接生效、会给他看一张卡；每次到点新开一条会话、自动带上这个插件，跑完看板出现在那次会话里。他没说要定时就别建。

## 做对的标准

- 用户在任何一步说「不是这样」，改，别辩解；他的原话写进 `taste.md` 或 `intent.md`。
- 每次给用户看东西，都是**真路径**；数据要么是真的、要么明说是样例。
- 用他的语言，大白话，不堆术语（「工作流」「技能」「卡片」可以说，「manifest」「frontmatter」别说）。
- 卡里不仿任何现成产品（包括 Kimi 的看板）；外框、圆角、卡片阴影是 Orbita 的，模板里不画。
- 不在用户的机器上装全局依赖（`pip install`、`npm i -g`），脚本只用标准库；真需要第三方库先问。
- 密钥、令牌不写进任何文件；需要时用 plugin.json 的 `userConfig`（`sensitive: true`），脚本从环境变量读。
- **诚实汇报验证了什么**：做完在对话里给一张**小结**：插件名、放在哪、技能列表、一句话怎么用、**没验证的是什么**（例如「只试跑了 5 条，没跑全量」「没有看卡片在玄主题下的样子」）。看不了图就说看不了图，别写「渲染正常」。

## 常见走偏（遇到先对照这里）

| 现象 | 原因 | 做法 |
|---|---|---|
| 还没聊定需求 / 工作流就在写脚本、爬数据 | 把第 5 步提前了 | 停。回第 3、4 步：清单一节节填，卡片一张张定 |
| 一次摆出好几个完整方向 | 把「换风格」当成了第一步 | 第一张卡只出一个，从他的品味出发；他对整体不满意才出 2 个方向 |
| 卡片模板里画了外框 / 圆角 / 阴影 | 忘了外框是宿主的 | 删掉；模板只管卡里面，根元素撑满整卡 |
| 卡片长得像某个现成产品 | 落到默认审美 | 回 board-style：从这张卡的内容重推颜色、字号、背景 |
| 找完现成的硬停下问「A 还是 B」 | 两个候选其实不冲突 | 自己定，一句话说出决定，继续 |
| 右栏没出现「正在做」 | 没调 `preview_plugin`，或路径不在工作区里，或清单读不了 | 看工具返回；路径必须在 `<工作区根>/plugins/<名字>/` |
| 右栏某节一直是「还没聊到」 | 清单里没写那一节 | 写进对应字段（`io` / `external` / `board`…），右栏几秒内自己出现 |
| `install_plugin` 报「outside this session's workspace」 | 插件不在工作区里 | 搬到 `<工作区根>/plugins/<名字>/` |
| 报 workflow 点名了不存在的技能 | `skill` 写的既不是技能目录名也不是 SKILL.md 里的 name | 改成本插件里真有的（草稿阶段 preview 只提醒不拦；装之前写好就对） |
| 卡一直是样例 / 空态 | 卡的 `data` 路径和脚本写的不一致 | `board.cards` 里那张卡的 `data` 就是脚本该写的路径 |
| 装好了但新对话里看不到技能 | 技能下一轮才加载；或 SKILL.md 缺 description | 看返回信息；补 description |
| 卡里点链接没反应 | 卡在沙盒里，不能跳转、不能联网 | 链接当文字显示，或发一个 `orbita:action` |
| 与用户已有技能重名 | 技能目录名撞了 | 改插件里的技能名（目录名和 SKILL.md 的 name 一起改） |
