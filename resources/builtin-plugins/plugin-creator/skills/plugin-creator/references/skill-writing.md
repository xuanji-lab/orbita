# 怎么写插件里的技能

改编自 skill-creator（Anthropic，Apache-2.0）的写法原则，删减并针对 Orbita 改写。完整版在用户的技能列表里（如果装了 `skill-creator`，可以读它的 SKILL.md 和 references/）。

技能 = 给“未来的另一个你”看的说明书。它读到这份说明时不知道今天的对话，所以要写到“冷读也能照做”。

## 一条技能的结构

```
skills/<slug>/
├── SKILL.md            必须。开头 frontmatter（name、description），后面是正文
├── references/         正文太长（>300 行）就拆到这里，在 SKILL.md 里写“什么时候读哪个”
├── scripts/            会反复用的确定性代码（取数据、转格式）
└── assets/             模板、示例文件
```

三层加载：`name + description` 永远在上下文里（所以要短而准）→ SKILL.md 正文在被触发时读（别超过 ~500 行）→ references / scripts 按需。

## description 是最重要的一行

它决定模型会不会想起这条技能。写成：**这条技能做什么 + 用户会怎么说 / 什么场景触发**，并且“推”一点（模型倾向于该用不用）。

差：`处理 arXiv 论文。`
好：`取 arXiv 某个分类的最新论文并给每篇写一句话摘要。用户说“看看今天 cs.CL 有什么新论文”“更新文献追踪”“arXiv 上有什么新东西”时一定使用，即使他没提 arXiv。不用于搜某一篇具体论文。`

不触发的情形也写进去（“不用于……”），能省下误触发。

## 正文怎么写

- **祈使句、具体、可复制**：“运行 `python3 scripts/fetch.py --category cs.CL --limit 5`，输出写到 `data/panel.json`”，而不是“获取数据”。
- **解释为什么**，少用全大写的 MUST / NEVER。模型懂道理，给它理由比给它禁令有效。
- **给格式时给模板**：产出长什么样，直接贴一个样例。
- **写进去踩过的坑**：这个接口会限流、这个字段可能为空、这个脚本在 Windows 上要用 `py`。
- 先写初稿，再用“第一次看到它的人”的眼睛读一遍，删掉不出力的话。

## 测试

写完拿 2–3 句**用户真实会说的话**（中文、口语、带他的项目名）当测试：实际按技能走一遍，看产出对不对。有可以客观检查的产出（文件、字段、条数）就写成验收清单（`intent.md`）逐条对。纯主观的产出（文风、设计）让用户看，别硬凑断言。

## 安全

技能里不放恶意代码、不让模型去绕过用户的意图、不偷偷往外发数据。技能的内容不该让用户意外——用户读 description 就能猜到它会做什么。
