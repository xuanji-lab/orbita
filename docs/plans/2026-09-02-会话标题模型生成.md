# C-3 · 会话标题由模型生成

> 批次 1 · C 组。参考实现：oh-my-pi fork 的 `title-generator.ts`（pi 本体没有
> auto-title，只有手动 `setSessionName`——核实过 `pi-main` 全部 `appendSessionInfo`
> 调用点，均为用户手动改名 / `--name` 参数）。批次 1 计划里提到的旧分支
> `auto-titler.ts` 已随 `wip/home-view-zcode` 删除，不可考，不追。

## 一句话

发完第一句，侧栏标题从「首句截断」变成模型概括的短标题；标题生成失败或被拒时
静默保留首句截断，绝不影响对话。

## 已定的五个判断点（2026-09-02 与用户对齐）

1. **触发时机：提交时，不等轮结束。** 首条消息提交出去就异步生成，与首轮对话并发。
   等轮结束的话，跑 10 分钟的任务标题要等 10 分钟；标题是侧栏导航索引，快比精重要。
   只喂用户消息本身，不带回答（oh-my-pi 的打磨史证明首条消息够用）。
2. **模型：当前会话同一个模型。** provider 与 key 已在 agent 进程（`create` 命令带
   `provider.apiKey`），零新配置。为标题引入「小模型角色」设施是过度抽象——
   oh-my-pi 需要它是因为 TUI 用户可能跑本地 350M 模型，我们没有这个场景。
3. **门禁：`titleSource === "derived"` 即允许尝试。** 失败 / 模型答 none 都不改
   `titleSource`，于是下一条用户消息自然重试——首试、失败重试、「你好」开头后补试、
   唤醒旧会话补试，一条规则全覆盖。「只试一次」反而要加状态。
4. **不做低信号预过滤。** oh-my-pi 的 60+ 词问候语表是给不听话的本地小模型设计的
   （其注释自述）；主模型靠 prompt 里「没实质任务答 `<title>none</title>`」就能拒答。
5. **改名（含改空）一律 `titleSource: "user"`，auto-title 永不覆盖。** 规则硬、
   无歧义；用户想要模型标题的恢复路径是改成自己想要的名字，不是让模型再猜一次。

## 机制（对齐 oh-my-pi，按需裁剪）

- **一次独立 LLM 调用**（pi-ai `/compat` 的 `completeSimple`），不复用主对话，
  不写 pi 扩展、不打 patch。
- **`<title>` 标记协议**：prompt 要求只输出 `<title>…</title>`；没实质任务答
  `<title>none</title>`。oh-my-pi 明确否决过强制 tool_call 返回 JSON 的方案——
  有的后端不支持 forced tool_choice，会复读 prompt 里的 JSON 示例当标题。
- **归一化**：取标记内容（无标记则剥残片取首行）→ 剥引号与尾标点 → 空 / `none`
  → null → 超 80 字符拒绝而非截断（那是模型在答用户的话，截断只会留下半个 blob）。
- **maxTokens 1024 硬上限**：不是目标值，是防思考型后端把 thinking 泄进回答时
  标记仍可达（oh-my-pi issue #4355 同款）。我们锁的 pi-ai 0.84.3 没有
  `disableReasoning` 字段（oh-my-pi 的新版才有），不传；标记提取兜住思考文本。
- **取消**：不做。生成几秒量级，utility 进程退出自然带走；会话被删时
  `setAutoTitle` 读不到 meta 悄悄不做，已有守卫兜底。

## 数据与链路

`SessionMeta` 加 `titleSource: "derived" | "auto" | "user"`（老 meta 缺失按
`derived` 解析）。链路：

```
renderer 发送 → main agentSubmit handler
  └─ sessions.needsAutoTitle(id)？→ host.generateTitle(id, text)（fire-and-forget）
       └─ agent 进程：in-flight 守卫 → completeSimple → 归一化
            └─ 事件 {type:"title", sessionId, title}
                 ├─ main recorder：setAutoTitle —— 写入时再查一次 titleSource
                 │   （生成在途时用户可能刚改名，不能盖），derived 才写 title+auto
                 └─ broadcast → renderer 收到即 refreshSessions()
```

标题调用在 **agent 进程**：API key 明文只在主进程 → agent 进程这一跳
（`agent/ipc.ts`），renderer 与主进程都不碰。

竞态窗口说明：`setAutoTitle` 与 `rename` 是两次「读 meta → 写 meta」，中间隔着
await，理论上可交错。与 store 现有全部 update 同款天花板，单进程事件循环下
窗口极小，不做加锁。

## 被否决的方案

- **等第一轮结束后生成**（批次 1 计划原案）：标题出现太慢；概括质量提升有限。
  以后嫌标题不准，另起一刀做「轮结束后带上下文刷新」（oh-my-pi 的
  `title.refreshOnReplan` 同思路），本刀不做。
- **给标题配专用小模型 / 模型角色**：设施成本 >> 每会话几十 token 的调用成本。
- **确定性问候语表**：为弱模型设计；主模型用 none 哨兵即可（见判断点 4）。
- **每会话只试一次**：需要额外「试过了」状态；`titleSource` 门禁天然支持自然重试。
- **改空名字退回 derived**：用户会看到「我清掉的名字几条消息后自己回来了」，
  解读成改名丢失。改名一律 user（见判断点 5）。
- **分支会话特殊处理**：`prepareBranch` 的 meta 记 `titleSource: "derived"`，
  统一规则不特判。效果：分支上发的下一条消息会用分支自己的走向重新起标题——
  这正是分支该有的行为；「（分支）」后缀本来就是占位符，被替换无害。

## 切分

- **PR1（协议）**：`shared/session.ts` 加 `TitleSource` + `parseSessionMeta` 默认值；
  `shared/agent-ipc.ts` 加 `generateTitle` 命令与 `title` 事件；测试。
- **PR2（实现）**：`src/agent/title.ts`（prompt 常量 + 归一化纯函数）、runtime
  接命令、`host-core.generateTitle`、`agentSubmit` 门禁、store 的
  `needsAutoTitle`/`setAutoTitle`/rename 置 user、recorder 落 `title` 事件、
  renderer 收事件刷新；测试 + UPDATE_NOTES。

## 这一刀不做什么

不做手动重新生成标题的入口；不做标题编辑之外的 meta 字段管理；不做轮结束后
的二次刷新；不做标题生成的取消与超时；不做用量统计（标题调用的 token 计入
会话统计是 pi 侧的事，它本来就不在这条链路上）。
