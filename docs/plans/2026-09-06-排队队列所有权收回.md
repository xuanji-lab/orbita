# 排队队列所有权收回：pi 不再持有排队状态

2026-09-06 · wafo 裁决「学 Proma，别自己造轮子」

## 为什么推倒重来

一晚上在排队卡上修了四轮，每修一个冒一个新的：

1. `move` 命令落空 —— runtime 漏改字段名，而 `src/agent` 是 typecheck 盲区
2. 连点两条「立即发送」，第二条被静默丢弃 —— `index` 是快照下标，队列一变就过期
3. 拖拽完全失效 —— 只排了 `queue` 数组没排 `queueOrder` 账本
4. 拖拽「一会行一会不行」、并发两个 Now「最后一起出去」—— 仍未修完

这些不是手滑，是**同一个结构性原因反复发作**：排队状态寄存在 pi 里。

### 结构性原因

pi 对排队队列只提供三件事：`getSteeringMessages()` / `getFollowUpMessages()` / `clearQueue()`，
外加 `steer(text)` / `followUp(text)` 逐条入队。**没有稳定 id，没有单条删除或挪位。**

于是我们被迫：

- **每次改动都是全清重放**（`clearQueue` + 逐条 push）。而 `clearQueue()` 自己就 emit 一次、
  每条重放再 emit 一次 → N 条队列打出 N+1 个事件 → UI 逐帧渲染出「先变空、再逐条长回来」。
- **只能用 `index` + `text` 对账**。两者都不稳定：下标随任何一次投递/清队前移，文本可重复。
- **顺序真源分裂成三份**：pi 的 `steering`/`followUp`、renderer 的 `queueOrder` 账本、
  `pendingSends`。三份靠文本互相匹配，任何一次落空都会让它们分叉。
- **投递时机不归我们管**：pi 的 post-run 循环看到队列非空就自动续轮，
  于是出现「我一条条点，最后两条自己一起飞了」。
- **命令并发不串行**（`void handle(command)`），而上面每一步都不是原子的。

**堵一个漏点会挪出另一个漏点**，因为漏的不是某一处判断，是「状态不归我们所有」这件事本身。

### 它还违反了项目自己的原则

`AGENTS.md`：

> **会话由我们自己存**（JSONL），pi 只当无状态循环——每轮把历史喂进去。

会话已经收回来了，排队队列没有。这是架构上的不一致，四个 bug 都从这道裂缝里长出来。

## 决定

**队列归我们，pi 只在真正要发的那一刻收到一条 prompt。**

对齐 Proma 的做法（`apps/electron/src/renderer/atoms/agent-atoms.ts:463`、
`components/agent/AgentView.tsx:2694+`）：队列是本地对象数组，每条带稳定 id，
所有操作按 id、O(1)、纯本地；后端只在发送时参与。

### 目标形状

```ts
interface QueuedMessage {
  id: string;                    // randomUUID，稳定身份
  kind: "text" | "compact";      // compact 是命令不是消息，保留区分
  text: string;
}
```

- 一条会话一个 `QueuedMessage[]`，**这是唯一真源**
- 发消息：`phase === "idle"` → 直接 submit；否则进队列（本地即时可见）
- 投递：收到 `phase idle` 事件后，队列非空就取第一条发 —— **时机由我们控制**
- 立即发送：`abort()` + 按 id 取出 + submit
- 撤回 / 拖拽 / 删除：纯本地数组操作，按 id

### 能删掉的东西

| 文件 / 概念 | 行数 | 为什么不再需要 |
|---|---|---|
| `src/agent/queue-edit.ts` | 59 | 不再有「全清重放」 |
| `src/agent/queue-locate.ts` | 31 | 有 id 就不需要按文本定位 |
| `src/agent/interrupt.ts` 的编排 | 68 | 简化成 abort + submit |
| `queue-drop.ts` 的差一格换算 | 31 | 按 id 拖放，不算下标 |
| `session-states` 的 `queueOrder` 账本 | ~39 处引用 | 只剩一个数组，不需要交错账本 |
| `queue` IPC 事件 | — | renderer 不再需要 pi 的队列快照 |
| `queueEdit` IPC 命令 | — | 队列操作不出进程 |
| `reorderQueueOptimistic` | ~40 | 本地就是真源，无所谓乐观 |

**这次重构减的代码比加的多。**

## 边界与已知取舍

- **排队消息只存在 renderer 内存**，刷新页面会丢。Proma 同样如此；排队消息生命周期是秒级，
  且用户看得见它在那儿。不为它引入持久化。
- **投递间隙**：从 `phase idle` 到我们发下一条，中间有一次 IPC 往返。用户会看到轮与轮之间
  有个短暂停顿。这其实比 pi 的无缝 drain 更好——轮的边界变得可见。
- **防御性冗余**：runtime 的 `submit` 在 `isStreaming` 时仍走 pi 的 followUp 入队。
  正常路径不会走到（renderer 只在 idle 时发），万一撞上也不丢消息，只是那一条不在我们的
  队列 UI 里显示。**不要**因此又去读 pi 的队列——那正是这次要断掉的耦合。
- **`/compact` 项**：它是命令不是消息，`kind` 区分。执行时机仍受机制约束（必须完全空闲）。

## 不做

- 队列持久化到磁盘
- 队列跨会话共享
- 键盘拖拽排序（现状是鼠标拖，撤回+重发是键盘可达的退路）
