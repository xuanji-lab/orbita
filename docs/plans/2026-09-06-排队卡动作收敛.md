# 排队卡动作收敛：一个动词「撤回」

2026-09-06 · review `theme-black-X` 一批时定案

## 问题

排队卡的就地编辑（点铅笔 → 那一行变 `<input>`）在跟 agent 的投递赛跑，三层都输：

1. 编辑第 1 条时，第 2、3 条可能被投递。
2. 编辑第 1 条时，**第 1 条自己**也可能被投递——本轮一结束队列就 drain，不看 UI 在不在编辑态。
3. **最狠的一层，是现在就有的 bug**：`rowKey` 是 `` `s${piIndex}:${text}` ``。队列**任何**一条被投递，
   后面所有条目的 `piIndex` 前移 → key 变 → React 卸载重建整行 → `editing` 状态与草稿一起蒸发。
   不需要正在编辑的那条被投递，队列动一下就够。

而且失败是静默的。`planQueueEdit` 对账不中就「原样重放」，注释明写「调用方无法区分
操作落空与正常重放」。用户改了半天按保存，UI 被 queue 事件校准回去，**一个字都不剩，也没有任何提示**。

`Cancel` 同样在丢字：删掉就没了，用户写的东西直接蒸发。

## 决定

排队卡上只保留两个动作，都是图标：

| 动作 | 图标 | 语义 |
|---|---|---|
| 撤回 | `undo-2` | 从队列移出 → 文字落进 composer 草稿（接在现有草稿后，换行分隔） |
| 立即发送 | `corner-down-left` | 不变，仍是 `interrupt`：清队列 → abort → 自己成为新一轮 |

**就地编辑整个删掉**（`<input>` / `autoFocus` / ✓✗ / Enter / Esc / `editQueued` / `editPendingSend`）。

理由：

- **竞态从根上消失**。一旦撤回，它就不在队列里了，没人跟你抢，想改多久改多久。
- **不新增概念**。`Cancel` 本来就在那儿，只是语义从「扔掉」变成「拿回来」——按钮数量不变，纯赚。
- **stack 是白送的**。连点三下撤回，三条依次落进输入框，用户自己决定怎么合并成一条。
- **消费者纪律**。pi 没有单条改/删的 API，`edit` 的实现是 `clearQueue` + 整队重放；
  为一条几十秒生命周期的消息养一套编辑 UI + 对账 + 重放，没有第二个消费者。

## 被否决的方案

### 一、编辑时阻塞投递

编辑态期间冻结队列 drain，改完再放行。否决：

- 要新 IPC + 新状态机，让 renderer 的局部 UI 状态反向锁住 runtime 的投递决策。
- agent 跑完了却卡着不动，用户第一反应是「死了？」；用户开着编辑框走开，会话就停在那儿。
- 与 `abort` 的既有哲学冲突——那条注释写着「**停止不该替用户放弃**」。
  反过来同样成立：**UI 的编辑态不该反向改变 runtime 的投递语义**。

### 二、就地编辑与撤回并存，让用户选

否决：两个动作的适用边界要用户自己判断（小改用编辑、大改用撤回），
而边界的真实依据是「agent 会不会在这几秒内跑完」——**用户无法预判的东西，不能拿来当选择的依据**。

### 三、保留就地编辑，只把三个 bug 修掉

修 `rowKey`、`<input>` 换 `<textarea>`、落空补提示。否决：三处都修完，
竞态窗口仍在（第 1、2 层修不掉），成本却比删掉它高。

## 已知取舍

- **丢掉「保顺位小改」**：撤回后重发会排到队尾，改错别字也一样。
  排队现实里通常只有 1~3 条，代价可接受。
- **撤回落空的重复风险**：点撤回的瞬间那条正好被投递，`planQueueEdit` 对账不中，
  队列原样重放，而文字已经进了 composer——用户可能再发一次。
  不为此改 IPC 契约（那要单独 PR）：文字明晃晃摆在输入框里，那条也已经作为
  user message 显形在对话里，用户看得见、能自己删。比现在「静默吞字」严格更好。
- **`/compact` 排队项没有「用户的话」可拿回**，它撤回就是单纯取消，不进草稿。

## 后续：对照 Proma 后的两处调整（2026-09-06 晚）

实测时拿 Proma 的 `AgentMessageQueue.tsx` / `pi-agent-adapter.ts` 做了对照。
图标选型（`CornerDownLeft` + `Undo2`）与「撤回追加到现有草稿」两家一致，
下面两处不一致且 Proma 是对的：

### 1. 空闲滞留态保留「立即发送」

原实现用 `haltedNote !== null` 把入口整个抹掉。Proma 的 `canSendQueuedNow`
不含「必须 streaming」，只用 `interruptsCurrentTurn` 换文案；后端也只在
`if (session.isStreaming)` 时才 abort。已对齐：保留入口，语义退化成「直接发」，
空闲时跳过 abort。

### 2. 排队项可调顺序

`queueEdit` 的 `edit` op 在删掉就地编辑后成了空位，换成 `move`。

交互形式反复了一次，最终跟 Proma 一致：**行首抓手拖拽**。

第一版做的是上下箭头按钮，理由是设计系统明写「重视键盘操作」而拖拽对键盘不可达。
实测被否（wafo 2026-09-06）：箭头挤在行尾的按钮区，位置和语义都别扭——
排序是「把它挪到那儿」，不是「对它执行一个动作」，放在动作区就暗示错了心智模型。
抓手在行首才读得出「这根条可以被拿起来」。

键盘可达性的账记在这里：当前版本排序**只能鼠标拖**。排队项本身是短命的（几十秒），
且撤回 + 重发始终是键盘可达的退路，所以不阻塞。真要补，加 `aria-grabbed` +
方向键移动比再摆两个常驻按钮干净。

单条时不给抓手（但保位）：没有可交换的对象，一个拖不动的抓手只是误导；
保位是为了行首对齐不因「能不能拖」而跳。

另一个定义：`as`（steer / followUp）按重放后的**位置**重新判定，不跟着条目走。
把一条挪进前面的 steering 段，它就变成插队——位置即投递时机，这正是用户把它拖过去的目的。

### 仍然不做：拆分「删除」与「撤回」

Proma 是三个键（立即 / 撤回 / 删除），我们合并成两个。
撤回之后文字就在输入框里，不想要清空即可；为「少按一下 Ctrl+A」多一个常驻按钮不划算
（wafo 2026-09-06 定）。

## 通用语言

`Now` 在两种排队项上是同名不同物，已确认不是 bug，但要落表（`docs/ubiquitous-language.md`）：

- pi 队列项上的 `Now` = **打断**（`interrupt`：清队列 → abort → 成为新一轮）
- `/compact` 项上的 `Now` = **立即执行**（`runPendingNow`，不打断任何东西）
