# 黑色皮肤 · 主题新增 black 档

> 分支：`theme-black-X`（自 `subagent-X` @ aab8568 切出）。
> 需求：用户想要「换一个黑色的皮肤」——不是把现有暗主题调黑，是要一套黑色外观。

## 已定的决定（2026-09-03，用户未另作表态时按本文执行）

1. **新增独立 black 档，dark 原样保留**。black 是真黑（底色阶从 `#000000` 起抬），
   dark 维持设计系统的冷近黑（`#111315` / `#1d2024`）。协议加档是加法，不动既有用户观感。
2. **black 是手动档**。`system` 跟随系统深浅仍只落 light/dark——系统只有两态，
   「深色映射到 dark 还是 black」无从判定，硬映射等于造第二个隐式默认。
3. **色彩理念：同一套「黑 + 黄」走到底**。yellow accent（`#e3c25a` 族）、
   墨色三级、状态色全部沿用 dark 的值不重调——换的是地，不是墨。
   black 相对 dark 的差异只在底色阶、发丝线、玻璃、阴影四处。
4. **玻璃阶梯延续「地越暗越要挡」**：light `.60` / dark `.70` / black `.78`。
   真黑档的承诺是纯黑地，壁纸渗进来一成就是脏黑；三层合成
   `1-(1-.78)^3 ≈ .99`，最里层与不透明黑无异。
5. **原生层把 black 映射成 dark**。`nativeTheme.themeSource` 只认三档
   （Electron 契约），直接传 black 会在启动时抛错（`applyNativeTheme` 先于窗口跑）。
   映射抽成纯函数放 `main/settings/native-theme.ts`，带测试；vibrancy 材质
   按深色走，纯黑部分由 renderer 的 `data-theme="black"` 自己画。
6. **shiki 双主题机制照抄 dark 的翻色规则**。shiki 内联 `--shiki-dark` 变量，
   black 底与 dark 底同样近黑，直接把 `data-theme="black"` 加进既有的
   翻色选择器，不生成第三套语法色。

## 被否决的方案

- **把 dark 底色调成纯黑**：改动最小，但所有暗主题用户的观感当场被改写，
  且 `system` 跟随系统深色时拿到的就是新黑底——等于替人做了选择。否。
- **只切现有「深色」不写码**：`#111315` 确实近黑，但用户明确开分支做皮肤工作，
  需求是一套可选择的黑色外观，不是指导航。否。
- **CSS 滤镜 / color-mix 把 dark 压黑**：token 失真、玻璃阶梯全乱，
  读代码读不出真实外观——违背「代码是唯一真源」。否。
- **black 档跟随系统深色**：见决定 2。否。

## 落地顺序（commit 切分）

1. `docs(plans)` —— 本文。
2. `feat(shared)` —— `THEME_PREFERENCES` 加 black（**shared 单独一个 commit**，
   不与实现混）；`settings.test.ts` 档位遍历自动覆盖。
3. `feat(main)` —— `native-theme.ts` 纯函数映射 + 测试；`ipc.ts` 改用它。
4. `feat(design-system)` —— `tokens/colors.css` / `glass.css` / `elevation.css`
   加 `:root[data-theme="black"]` 块；readme 的 Colour / Transparency /
   「One light theme…」三处规格同步（设计系统是真源，token 与规格必须同 PR）。
5. `feat(renderer)` —— `useTheme` 解析透传 black；`SettingsView` 四档标签 +
   hint；`styles.css` 三处 shiki 翻色选择器加 black。
6. `docs(update-notes)` —— 用户可见变更条目。

## 已知边界

- macOS 真玻璃（vibrancy + 透明窗口）下 black 的观感取决于桌面壁纸；Windows 无原生透明，
  底色即真值，black 在 Windows 上就是深蓝黑窗口。
- `data-light-background` 五个浅底变体（readme「One light theme…」条）与 black
  互不相干——那是浅主题内部变体，这是第三套主题档。

## 修订（2026-09-03 当天，用户验收反馈「又有点太黑了。参考 github 的颜色」）

- **底色阶从真黑 `#000` 起抬换成 GitHub dark 系**：app `#0d1117`（canvas）、
  panel `#161b22`（subtle）、strong 边线 `#30363d`（border.default），中间值按
  dark 主题同构的阶梯内插。决定 1 的「真黑」表述作废，「独立 black 档」不变。
- **玻璃从 .78 回到 .70**：地面不再是纯黑，「挡最狠」的前提消失。black 与 dark
  同透明度、不同色温（冷蓝黑 vs 中性石墨）。决定 4 作废，readme 透明度段同步改。
- **决定 3 原样成立**：黄 accent、墨色、状态色沿用 dark——这一轮只退烧地面，
  不动墨。决定 2、5、6 不受影响。

## 修订二（2026-09-03 当天，用户再反馈「当前的黑色还是不太对」）

对照 GitHub 真实做法找到两处偏差：

- **玻璃 tint 用错了色**：dark 主题的配方是「tint = 自己的 panel 色」
  （rgba(29,32,36,.7) 即 #1d2024），首版 black 拿 canvas 色 rgba(13,17,23) 当 tint，
  而 Windows 下 body 就是 canvas 色——两层玻璃叠完仍是同一块平色，层级全塌。
  改为 tint = #161b22（canvas.subtle），阶梯恢复「页面深、卡片浅」的单调爬升。
- **墨色换成 GitHub 的文字三级** #e6edf3 / #9198a1 / #656d76：GitHub 的文字层级
  本身就是它观感的一半，沿用自家暗主题的墨（secondary #b9c0c8 偏亮偏蓝）读起来
  「不像」。修订一的「换的是地，不是墨」至此部分作废——**地与墨都是 GitHub 的，
  唯一留给品牌的是黄 accent**。`--color-text-inverse` 随 primary 取反改 #0d1117
  （应用内暂无消费者，纯规格一致性）。
- chat 面三值随语义对位：消息卡 = canvas.subtle #161b22，代码/审批条底 #1c242e，
  控制面 #11171e。状态色维持不动（dark 那套本就取自 GitHub 旧版 Primer）。

## 修订三（2026-09-03 当天，用户三验「黑色再深一点」）

- 中性 ramp（地面 + 发丝线 + chat 面）**整体 ×0.78**：页面 #0a0d12、panel #11151a、
  strong 线 #252a30——落在被否的两端之间（#000000「太黑了」/ GitHub default
  「再深一点」）。阶梯步进、hover 差、线与地的对比全部按比例保持，
  一次换掉整条 ramp 而不是单点压暗某个面。
- 玻璃 tint 跟随新 panel 色 rgba(17,21,26,.7)，「tint = panel 色」配方不变，
  层叠仍是 #0a0d12 → #11151a 的单调爬升。
- 墨、accent、状态色不动。

## 修订四（2026-09-03 当天，用户点名阵营「中性深灰」）

盘点了主流深色的四个阵营（纯黑 OLED / 中性深灰 / 蓝黑 / 编辑器主题色）后，
用户选定**中性深灰**——Material `#121212` 面、`#1e1e1e` 卡（VS Code 编辑器同值）、
无色相发丝线 #232323 / #2a2a2a / #303030。

- **色相离场**：蓝黑味随 GitHub 地面一起走——「发闷」的病根是色相不是深度
  （修订一、二都在调深度，没治到这一层）。
- **墨换 Google 暗色三级** #e8eaed / #9aa0a6 / #80868b：与本阵营同源
  （GitHub 三级偏蓝）。链接 / info 蓝换成 Google 的 #8ab4f8 对齐阵营。
- 玻璃 tint 跟随新 panel 色 rgba(30,30,30,.7)，配方不变；danger/warning/success
  是色相编码的中性资产，跨阵营沿用。黄 accent 仍不动。

## 修订五（2026-09-03 当天，定稿）

中性灰被否：「有点泛黄」。解释——黄 accent 在这套界面里面积不小（选中底、
soft 底、模式芯片），压在纯中性灰上发生同时对比，整片灰被带暖；
蓝黑地与黄是互补对，黄反而衬得干净。

- 用户点名 **GitHub #0d1117 / #161b22**，black 档回到**修订二的完整值**
  （GitHub default 全强度 + GitHub 墨 + panel 色 tint）。
- 修订三「再深一点 ×0.78」作废——「泛黄」与「加深」两个诉求冲突时，
  以最后一次反馈为准：default 全强度。
- 教训归档：这套界面带着大面积黄 accent，**中性无相的地配不住它**；
  地面必须自带一点互补色相（蓝黑）去平衡。真黑、纯灰两案均已试并被否。

## 修订六（2026-09-03 当天，看对比页后两暗档一起定）

GitHub default 也被否（「有点蓝、看着眼睛不舒服、有点亮」）。做了六候选渲染
对比页（同构迷你界面：选中行黄底、消息卡、代码块、链接、黄按钮），用户点名
**⑤ Gruvbox 暖黑** 与 **⑥ Vercel 极暗中性**，直接替换现有 dark 与 black：

- **映射按明暗阶梯语义**：dark ← ⑤（较亮的暖黑 #1d2021/#282828）、
  black ← ⑥（最暗的中性 #0a0a0a/#111111）——「dark 比 black 亮一档」的
  既有关系保持。
- **修订五的教训更正**：「地面必须自带互补蓝黑」下得过强——暖黑（同黄族）
  与极暗中性都是用户实看后的选择。泛黄的真正边界条件待验收：#121212 泛黄，
  更暗的 #0a0a0a 未必；退手备好（地加一丝冷偏 #0a0b0c，或降 accent-soft alpha）。
- **dark 是 system 档的落点**：跟随系统深色的用户会直接拿到新暖黑——这是
  「替换 dark」的核心代价，已言明；原石墨蓝黑 #111315/#1d2024 退役。
- shiki 翻色选择器、nativeTheme 映射、四档契约、renderer/main/shared 代码
  **全部零改动**——主题观感只住在 token 块里，这是本次替换便宜的根因。

## 修订七（2026-09-03 当天，定名与柔化）

三件事：**system 改随 black**、**两档定名**、**Warm 柔化**。

- **system 的深色落点从 dark 改为 black**（用户指定「system 跟随 black」）。
  useTheme 一行；nativeTheme 不动（system 仍透传，Electron 自己跟系统深浅）。
  至此 dark 与 black 都是纯手动档——修订二「black 是手动档」的决定被用户推翻，
  决定 2 作废。
- **定名只动设置面的 label，不动内部值**：dark → **Warm**、black → **Ink**。
  值（`dark`/`black`）是 settings.json 里的 API，改名就要写迁移；label 改名
  零迁移零风险。用户要的是「换个名字」，落点在看得见的那层。
- **Warm 柔化**：「过于黄色」的来源是全饱和暖米字 #ebdbb2（画面上面积最大的
  暖色），不是地面——墨降到半饱和 #dfd9c9 / #b0aa9c / #8b877c，悬停与边线
  中性化（#32302f→#303332 等），黄 accent 的 wash 0.18→0.14。地面三值未动。
- 修订六「shiki 零改动」依然成立：两档 id 没变，翻色选择器照常命中。

## 修订九（2026-09-03 当天，黄 wash 压到 5%）

三个黄 wash token（bg-active / accent-soft / mode-active-bg）统一 0.10 → 0.05。
Warm 档的选中态从此**主要靠字重与文字色标记**（设计系统本就规定 active is

## 修订十（2026-09-04，手动验证反馈的修复）

验证结论：1/3/4 与二正常；三暴露三处对比度问题；二暴露切换过渡问题。四修：

- **主题切换闪/跳**（系统深浅实时切换：深→浅瞬跳、浅→深闪一帧）：useTheme
  写 `data-theme` 时包一层 `document.startViewTransition` 整窗交叉淡入；
  首帧应用不加动画，`prefers-reduced-motion` 时跳过（设计系统动效纪律）。
- **函数在代码里隐身**：shiki 的 github-dark 是旧版调色板，只有函数**声明**
  （entity.name → #b392f0）有规则，**调用位**（代码里的大多数 `foo()`）没有
  规则、落到与正文同色的默认前景 #e1e4e8。给暗色主题补一条规则：函数
  （声明+调用）统一 GitHub 新版函数紫 #d2a8ff。浅色不动。
- **文件名与正文同色**：read/write/edit/ls 的路径摘要与 find/ls 行的文件名
  从 text-primary/secondary 改为 `--color-chat-link`（Light=蓝、Warm=青、
  Ink=蓝），与正文墨色分层。grep 行的路径保持 tertiary——那是「定位弱于
  内容」的既有层级，不是本次问题。
- **accent 黄冷化加深**：#e3c25a（h44 l62，橙味重）→ **#d6c245**（h52 l55），
  hover 版 #f0d375 → #e2d05e，三处 wash 基色同步 rgba(214,194,69,·)，两档
  焦点环对齐。「太暖/泛黄」的最后来源就是这粒橙味重的黄。

## 修订十一（2026-09-04，差异化补完）

修订十修了工具行与函数，用户复验后指出**正文里的机器内容**仍是同色：
内联 code（文件名、路径、标识符）完全继承正文墨色，深色下芯片底与地面只差
几阶、形同虚设。

- **行内 code 用链接色**（`.chat-md :not(pre) > code` → --color-chat-link）：
  「机器内容」从此有自己的色相——Light 蓝 / Warm 青 / Ink 蓝。只上行内，
  块内是语法色的领地，无语法色的裸块继承正文色。
- **代码块加发丝线**：muted 底与深色地面的差阶太浅，块的边界改由 1px
  border-subtle 负责（readme：borders are always 1px hairlines）。
- 至此对话区的分层是：正文墨色 → 行内机器内容链接色 → 代码块（框 + 语法色）。
  函数紫（修订十）与工具行路径色不变。
