# C-2 · 会话可从某条消息另起一支

> 批次 1 计划：`2026-08-30-批次1-单agent深化.md` C 组。本文记录定稿设计、关键事实
> 与被否决的方案。实现于 2026-09-02，分支 `batch-1-X`。

## 定稿语义

在**每轮 agent 最终完整输出**下面出一条「从这里分支」按钮。点击后开出一条新会话，
内容 = 该回答及之前的全部（含工具结果与压缩界碑）；原会话不动。自动切过去，
标题 = 原标题 +「（分支）」，meta 继承 cwd / workspaceId / provider / model / mode
（`pinned=false`、不继承归档），**不加任何关联字段**。

按钮显示规则：

- 消息未完整（streaming）→ 无按钮；
- 轮中中间回答 → 无按钮（被轮末回答顶替）；
- 任何工具还在跑 → 全部禁用，落定自动恢复（工具结果没齐的裁点是畸形上下文：
  assistant 带 toolCall 而无 toolResult，LLM API 拒收）；
- 被打断但带正文、且其工具调用都有完结记录的轮末消息 → 可分支。

锚点必须是 assistant（带 ≥1 非空 text 块）。「在最后一条回答后另起」（克隆语义）
天然被覆盖：它就是最后那个锚点。

## 关键事实（设计的前提，都已实证）

1. **两本账没有 id 映射，也不可能有。** pi-ai 的 `Message` 没有 id，
   ORBITA 的消息 id 是 adapter 自铸的 UUID（`transcript-adapter.ts`），
   pi 的 entry id 从事件流里拿不到。
2. **按位对应成立。** 把两边都过滤成 user/assistant 序列后逐位相等——
   2026-09-01 对磁盘上 72 条真实会话全量验证：70 条完全一致，含压缩的 16 条全部一致
   （compaction 条目也 1:1）。两条分歧：① 我们多记了 pi 没落的「status=error 且内容
   为空」的失败尾巴（首轮 provider 失败）——角色抽取时跳过它即消解；② 同一毫秒内
   user/assistant 落账顺序漂移（停止+新消息竞态）——罕见，由对账守卫兜底。
3. **pi 无 seed API。** `createAgentSession` 不能带初始消息；续会话唯一方式是把 pi
   自己的文件还给它。所以分支必须在 pi 侧裁一份新文件——`SessionManager
   .createBranchedSession(leafId)` 正好做这件事（root→leaf 路径整段复制、parentId
   拉直、header 的 parentSession 指回源文件）。

## 数据通路（IPC 四层）

```
renderer ─ session:branch(sessionId, anchorItemId)
main     ─ store.prepareBranch()：定位锚点、截前缀、抽角色序列、起好新 meta（只读不写）
         ─ host.branchSession() → agent 进程发 branch 命令（源 pi 文件 + roles）
agent    ─ 一次性 SessionManager.open 源文件 → planBranchCut 对账 + 选裁点
         ─ createBranchedSession(裁点) → created 事件回传新 pi 文件
main     ─ store.commitBranch()：原子写新 meta（补 pi 文件）+ 前缀整写初始 JSONL
renderer ─ 切到新会话（走既有 resume 路径，首次发言把 pi 分支文件还给 pi）
```

顺序保证：pi 文件先落地、本地会话后落盘——中途失败最多留一个**孤儿 pi 文件**
（不可见、无害），不出现「看得见历史但 pi 没有前文」的半残会话。

对账守卫（`agent/branch-cut.ts`，纯函数）：本地角色序列与 pi 文件**前 N 位逐位比对**，
不合即抛错拒绝。裁点 = 锚点条目向后连吃 `message:toolResult` 条目，遇到
user / assistant / compaction / 非消息条目即停。

## 已知天花板（写进了代码注释）

- 罕见落账漂移会让个别会话分支被守卫拒绝——**拒绝优于切错**：切错意味着用户
  以为带着 A 的前文，实际带的是 B 的。
- 分支会话的累计 token / 花费继承自 pi 分支文件（pi 对分支会话的同款行为）。
- `createBranchedSession` 会把 manager 实例**原地换绑**到新文件——绝不能用在活会话
  的 manager 上（后续追加会写进分支文件）；分支永远开一次性 manager。
- 源会话正在跑时分支是安全的：只读源文件、只写新文件，互不干扰（idle-only 到
  「工具跑着才禁用」的放宽就建立在这上面）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 按钮放用户消息上、排他截断 + 原文预填输入框 | 用户裁决：入口应在 agent 输出下、语义应为「这一轮及之前全带」；预填草稿也就没有对象了 |
| pi `/fork` 式包含锚点为下一条用户消息（悬空 user 收尾） | 连续两条 user 的上下文形态不干净；「问错了重来」由「分支到上一轮 + 重新问」覆盖 |
| `SessionMeta` 加 `branchedFrom` 关联字段 | AGENTS 既定边界：父子会话字段等真开编排再加。不加字段 ⇒ 计划里写的 0-4 前向兼容依赖**整个消失**，标题后缀足够区分 |
| 手拼 pi 格式 JSONL（不经过 pi 的 API） | 耦合 pi 内部文件格式，换内核全报废；`createBranchedSession` 是公开 API 且行为正好吻合 |
| 每条带正文的 assistant 消息都可分支 | 用户裁决（Q8）：只有轮末「最终完整输出」配按钮；轮中消息是过程不是「一次输出」 |
| 仅完全 idle 才可分支 | 用户裁决（Q3）：运行中可点上一轮；安全性由「工具跑着禁用」精确保证，不必整个会话锁死 |
| 事后补一张「两本账 id 映射表」 | pi 事件流里拿不到 entry id，映射表无从记起；按位对账已足够且被实证 |
