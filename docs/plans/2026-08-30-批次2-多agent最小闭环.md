# 批次 2 · 老板 + 干活的（多 agent 最小闭环）

> 5 刀。**这一批跨过单 agent 的边界**——`registerTool` 出现第一个调用点。
>
> **成熟度低于批次 0 和 1**：2-4 压着一个尚未验证的前提，见下。
> 写出来是为了让方向可见、让接口能提前对齐，不是说它已经可以照着做完。

## 这一批的目标

让用户第一次真的看到**两个 agent 协作完成一件事**。

全表最小的一批（5 刀），这是故意的：在这件事真的发生一次之前，
后面所有编排设计都是纸上的。让它尽早发生，比把它设计得更完整重要。

**验收场景**：
> 「用 scout 找出认证相关的代码，然后让 reviewer 审一遍」
> → 两张委派卡片依次亮起，scout 的搜索过程流式可见，reviewer 要改文件时父窗口弹审批条。

---

## ⚠️ 动手前必须先验掉的一件事

**2-4 的形态取决于这个答案，两种答案的工作量差好几倍。**

先把两件事分清楚：

```text
✓ 已验证   同一个 utility 进程里跑多个 AgentSession
           现有代码每天在做——用户开两个 task 就是两条。
           证据：runtime.ts:122 每 session 各自 ModelRuntime.create({})
                runtime.ts:174 sessions.set(...) 每次 create 都新建

? 未验证   在 pi 的【工具执行回调内部】开一个新 session 并 await 它跑完
           这才是委派的真实形态，和上面不是一回事
```

**风险在重入与阻塞**：工具执行本身跑在 agent-loop 内部，此时再起一个 loop 并等它结束——
会不会死锁？父会话 abort 时能不能穿透到子会话？

**最便宜的验证（十几行，半小时）**：
在 `runtime.ts` 的扩展工厂里 `registerTool` 一个玩具工具，
它的 `execute()` 里 `createAgentSessionFromServices` 开一条新 session、
`prompt("说一句话")`、等它 settled、把文本返回。跑一次看：

- 会不会卡死
- 父会话的事件还流不流
- 父 abort 时子会话停不停

**两种结果对应的路**：

| 结果 | 2-4 变成 | 量级 |
|---|---|---|
| 能跑 | 注册一个工具 + 生命周期管理 | 按本清单做 |
| 卡死 | 退回「起 pi CLI 子进程」，**并要处理打包后 Electron 里没有 `pi` 可执行文件** | 大得多，要重排 |

> pi 官方的 subagent 示例走的是第二条路（`examples/extensions/subagent/index.ts:346`
> `spawn(invocation.command, ...)`）。它在 dev 下能用是因为 `node_modules/.bin/pi` 存在，
> **打包后的 Electron 不保证有**。所以我们优先试第一条路。

## 2-1 · 委派的状态机（纯函数，约 120 行）

**做什么**：`src/orchestration/delegation-state.ts`
五个状态 `pending | running | completed | failed | cancelled`，**终态冻结**（进了终态不能再改）。

**为什么单独一刀**：它是纯逻辑，零 IO，可以穷举测试。混在工具实现里就测不动了。

**怎么验**：状态转移表**穷举**——合法转移列全，非法转移必须 throw。

**不要顺手做**：不要在这一刀里碰 pi；不要设计消息格式（那是 2-5）。

---

## 2-2 · 派活预算（纯函数，约 80 行）

**做什么**：`src/orchestration/dispatch-budget.ts`

三件事：
- **深度上限**——子 agent 不能再派子 agent。Proma 的做法是硬上限 1（`delegationDepth > 0` 直接拒绝）
- **并发上限**——同时最多几个。pi 官方示例用 `MAX_PARALLEL_TASKS = 8` / `MAX_CONCURRENCY = 4`
- **幂等键**——同一个 `toolCallId` 重复到达时不重复建会话

**幂等这条是必需品不是优化。** Proma 源码注释原文：
「Pi 的 provider/retry 流可能重放同一个 tool call；委派会创建真实会话，必须幂等」。
**架构文档里完全没有这一条**，是踩出来的。

**怎么验**：depth=1 时拒绝；同 `toolCallId` 第二次返回同一个结果不新建；并发满时排队而不是拒绝。

**不要顺手做**：不要做 token 预算与返还（无 token 预算时无意义）。

## 2-3 · 角色定义解析（纯函数，约 150 行）

**做什么**：`src/orchestration/agent-def.ts`
读 md + YAML frontmatter：`name` / `description` / `tools` / `model`。

**pi 已提供**：`parseFrontmatter` / `stripFrontmatter`（`utils/frontmatter`）。
**参考实现现成**：`node_modules/@earendil-works/pi-coding-agent/examples/extensions/subagent/agents.ts`（157 行），
含 `tools` 两种写法的归一（`tools: read, bash` 与 `tools: [read, bash]` 都合法）。
同目录 `agents/` 下有 scout / planner / reviewer 三个可直接借鉴的角色文件。

**怎么验**：坏 YAML 不崩、缺字段有默认、两种 `tools` 写法都认、
**一个文件坏掉不影响同目录其它角色**（这条是参考实现里明确写的）。

**不要顺手做**：不要做角色的增删改 UI（批次 3）；不要做项目级角色目录与信任确认（批次 3）。

## 2-4 · delegate 工具 ⚠️ 唯一的层 2，前提待验

**做什么**：`registerTool` 注册一个 `delegate` 工具，在同一 utility 进程内开第二个 `AgentSession`。

**这是整个项目第一次向 pi 注册新能力**——边界二的分水岭。
`grep -rn "registerTool" src/` 从 0 变成 1。

**改哪里**
- `src/agent/runtime.ts` — 现有的 `orbita-permission` 扩展工厂里加 `pi.registerTool(...)`，
  或另起一个扩展（**建议另起**，权限闸门与委派是两件事）
- `src/orchestration/delegate-tool.ts` — 工具定义与执行（接线，允许 import pi）
- `src/orchestration/child-session.ts` — 子会话的创建与生命周期（接线）

**同一刀必须捆绑的三件**（不能延后过夜）：

1. **子 agent 的工具调用走同一条审批闸门** —— `bash` 全开的安全前提。
   子 agent 绕过审批就是安全回归。现有闸门在 `src/agent/permission.ts`，复用它。
2. **abort 穿透** —— 父会话中止时销毁全部子会话，不留孤儿。
3. **结果截断上限** —— 子 agent 干 30 轮的全部内容不能整包塞回父上下文。
   Proma 的做法是取最后一条 assistant 文本 + 50KB 上限，全文 18 行。

**怎么验**：验收场景那一条真的跑通；父 abort 时子会话确实停；
子 agent 调 `write` 时父窗口弹审批条。

**不要顺手做**：不要做并行/串联（批次 3）；不要做质检（批次 4）；
不要在这一刀里设计 Preset（批次 7）。

## 2-5 · 委派过程流式可见

**做什么**：子 agent 的事件翻成父会话 transcript 里的条目，卡片可折叠展开。

**依赖 0-3 的 `visibility` 字段**——委派消息标 `delegated`。
肖志锋那边没做完的话，自己先加，合并时留一份。

**改哪里**
- `src/agent/transcript-adapter.ts` — 子会话事件 → 带 `visibility: "delegated"` 的条目
- `ChatView.tsx` — 委派卡片（角色名 + 状态 + 折叠/展开）

**可以直接照搬形状的**：刚做完的 `ToolLine`（`ChatView.tsx`）——
折叠一行、点开看内容、状态用图标 + 文字表达。委派卡片是它的放大版。
**图标只用 lucide，不用 emoji。**

**不要顺手做**：不要做拓扑图（旧分支有一版 React Flow 的，等真有并行了再说）；
不要做子会话的独立入口（点进去单独看，那是后面的）。
