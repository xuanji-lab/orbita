# 批次 0 · 让 agent 干的事看得见、留得住

> 第二版。**上一版按技术层次横切分刀（协议→采集→存储→渲染），10 刀里 7 刀看不出变化——那是错的**，
> 它违反了本项目自己的纪律「一刀必须有真实调用点」。这一版按功能纵切，**4 刀，前 2 刀都能当场演示**。

## 先说清楚三件事

**批次 ≠ PR。** 批次是一组相关功能；**一刀 ≈ 一个 PR**；一个功能跨几个文件是正常的，不叫大重构。

**大刀的定义是"一次改很多不相干的东西"，不是"改了几个文件"。**
一个功能从事件采集到界面显示要穿过 4 个文件，那是它的自然范围，硬拆开反而让前 3 个 PR 没有意义。

**这一批不是"为多 agent 做准备"。** 下面两个功能本身就是用户要的东西：
看得到 agent 执行的命令返回了什么、内部消息不再混进对话。
它们**顺便**也是多 agent 的前置——但先做它们的理由是「本来就该做，而且越晚做越贵」，不是「为了后面」。

## 刀 0-1 · 看得到 agent 执行的命令返回了什么

### 演示

跑 `bun run dev`，让 agent 执行 `ls src`。

- **现在**：只显示一行"调用了 ls"，不知道它看到了什么
- **做完**：那一行可以点开，里面是完整的 ls 输出。执行 `grep` 也一样，报错的命令能看出是失败的

### 为什么现在做（而不是以后）

不是"为多 agent 准备"。是这三条：

1. **产品把"可追溯"当卖点，而现在磁盘上的记录是不完整的。** 越晚补，补不回来的历史越多。
2. **设计系统点名要求**：「思考、工具调用、文件阅读都折叠成一行、**点击才展开**」——折叠早做了，展开一直没做。
3. 顺便：派活的结果本质上就是一条工具结果，这条链通了多 agent 才有地方放回传。

### 改哪里

| 文件 | 改什么 |
|---|---|
| `src/agent/runtime.ts` | `asAdaptable()`（第 100 行）现在只放行三个 `message_*` 事件，加上 `tool_execution_start / update / end` |
| `src/agent/transcript-adapter.ts` | 加 tool 事件分支，产出 `ToolTranscriptItem` |
| `src/renderer/src/features/chat/ChatView.tsx` | `Item()` 加 tool 分支；`ProcessLine`（约 396 行）现在是个 `<p>`，正文区 `onClick` 零命中——加折叠/展开 |

### 已核实的前提（不用再查）

- 这三个事件就在 `AgentEvent` 里（`pi-agent-core/dist/types.d.ts:396-411`），`session.subscribe()` 直接拿得到，**不需要写 pi 扩展**
- **类型不用自己写**：`ToolTranscriptItem` 已在 `pi-protocol/dist/schemas.d.ts:282`，字段齐全（`toolCallId / toolName / input / content / details / usage`）。`TranscriptItem` 是三支联合，我们只生产了两支
- **`src/shared/` 一行都不用改**——`AgentEvent.progress` 用的就是 pi-protocol 的类型，本来就装得下第三支

### 怎么验

- 手动：上面那个演示
- 自动：`transcript-adapter.test.ts` 加用例——喂 `tool_execution_start → end`，断言 `toolCallId / toolName / input / content` 对得上；`isError: true` 时状态正确
- 纯函数测试：折叠态摘要的生成（"读取了 3 个文件"这类）单独可测

### 不要顺手做

- **不要按工具类型做定制渲染**（Edit 的 diff、grep 的高亮）—— 批次 1
- 不要顺手把 `usage`（token / 花费）填上 —— 批次 1
- 不要顺手加自动滚动 —— 批次 1
- 不要动落盘（下一刀）

- **做完**：重开会话，工具结果还在原位；导出的 Markdown 里每个工具调用都带着它返回的内容

### 改哪里

| 文件 | 改什么 |

**建议截断并标注「（已截断，共 N 行）」**，因为导出是给人读的。但这是判断不是规定。

### 怎么验

## 刀 0-3 · 内部消息不再混进对话

### 演示

跑一条足够长的会话，让它触发一次上下文压缩。

- **现在**：压缩产生的摘要、系统注入的提示，和你自己的对话混在一起显示
- **做完**：对话里只有你和 agent 的往来，内部消息不出现

### 为什么现在做

这是本批唯一一条**理由主要在后面**的刀，但它值得：

`visibility` 是**投影规则**——它决定哪些记录进用户视图。
**现在加是 1 个字段；等做委派时加，要回填全部历史会话文件**才能判断旧记录该不该显示。

而且单 agent 自己就需要它——上面那个演示就是现在真实存在的问题。

### 改哪里

按项目既有规则「`src/shared/` 的改动单独成 PR」，**这一刀是两个 PR，同批合并**：

| PR | 文件 | 改什么 |
|---|---|---|
| 前置（小） | `src/shared/session.ts` | 加 `visibility: user \| internal \| delegated` |
| 实现 | `useChatSession.ts` / `ChatView.tsx` + 产生内部消息的地方 | 渲染前过滤；压缩摘要与系统注入标 `internal` |

### 需要一个设计判断（这一刀最难的地方）

`TranscriptItem` 是 pi-protocol 的类型，**我们不能直接往里加字段**。两条路：

| 做法 | 好处 | 代价 |
|---|---|---|
| 落盘时包一层 `{ item, visibility }` | 不碰上游类型，换 pi 版本不受影响 | 读时多一层解包；旧的 `.jsonl` 行要兼容 |
| 自己定义一个扩展类型 | 读写直接 | 与上游分叉，上游加字段时要跟 |

**建议第一条**（包一层）：会话记录是我们自己的东西，不该被上游类型形状绑住——与 guideline §四「我们自己存」一致。
**这是判断不是规定，定了写进 PR 描述。**

### 怎么验

- 手动：上面那个演示
- 自动：旧记录读出来默认算 `user`；坏值不崩退回默认；过滤逻辑抽成纯函数单测

### 不要顺手做

- 不要做"显示内部消息"的开关（等有人要再说）
- **不要顺手加 `parentSessionId` 这类归因字段** —— 批次 2 的事，现在加就是没有消费者的字段

## 刀 0-4 · 工程债：内存泄漏 + 三处回归测试

**这一刀不装成功能。** 它就是还债，界面上看不出任何变化。

### 债务 A · 会话关掉了但没释放

`AgentCommand` 有 `dispose` 分支，`runtime.ts:238-240` 有完整处理（退订 + `session.dispose()` + 从 Map 删除），
**但 `AgentHost` 里没有任何代码发出这条命令**——已核实它的公开方法只有
`createSession / listBuiltins / submit / setMode / answerPermission / abort / dispose()`，其中 `dispose()` 是杀整个进程的。

所以每建一条会话就进 `sessions` Map，永远不出来。每条持有一个 pi 会话 + 一个模型运行时 + 一个未退订的订阅。
**开 20 条任务，20 个 pi 会话全活到你退出应用。**

- 改：`src/main/agent/host.ts` 加 `disposeSession(sessionId)`；在会话关闭/删除处调用
- 验：建 3 条销毁 3 条，断言 runtime 侧 Map 归零
- 不要顺手做：不要做"会话池"或"最多保留 N 条"策略；不要改 `abort` 的语义（中止 ≠ 销毁）

### 债务 B · 三处已经咬过人的地方没有回归测试

当前 4,857 行源码无测试（占 76%），而这三处都出过事故、修完都没留测试：

| 位置 | 出过什么事 |
|---|---|
| `AgentHost` 的 `pendingCreates` | 创建请求与 `created` 事件的竞态 |
| 内建 provider 目录 | 到达时机竞态 |
| `useChatSession` 的 sessionId 过滤 | 跨会话事件串台 |

实测返工率 30%，全靠事后手测发现。**多 agent 会在这三处之上再叠一层。**

- 改：三个新测试文件
- 不要顺手做：不要为了"更好测"重构被测代码——先用现有形状写，真写不了再谈

## 给执行者的三条

1. **超出"改哪里"的范围时，先问一句：这是同一个功能的自然延伸，还是另一件事？**
   同一个功能跨几个文件 —— 继续做。另一件事 —— 拆出去。
2. **"不要顺手做"被违反时不用觉得可惜。** 那些事都在后面的批次里，不会丢。
3. **每个 PR 描述里写一句"这一刀不做什么"。** 它比"做了什么"更能防止范围膨胀。
