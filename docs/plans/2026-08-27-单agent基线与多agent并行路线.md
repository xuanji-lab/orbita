# ORBITA 开发路线 · 边界与批次

> 2026-08-30 第四版。**这份文档回答"为什么"，不回答"怎么做"。**
> 怎么做看同目录的 `2026-08-30-批次0-执行清单.md`——执行清单只展开眼下要干的那一批，后面的等到了再展开。
> （把 80 刀一次全写成执行规格，本身就是一次性大重构的思维。）

**谁读**：wafo 用它决策；肖志锋用它判断"我手上这一刀为什么排在这里、什么时候该停下来问"。

## 一、两条边界

### 边界一 · 什么时候算进了多 agent

**判据：有没有第二个 agent 会话，且两者之间有任务下达与结果回传。**

| 形态 | 归属 | 为什么 |
|---|---|---|
| 会话分支 / fork | 单 agent | 时间线分叉，没有任务传递 |
| 多标签同时跑几条 | 单 agent | 几条互不相干的会话 |
| 后台无界面跑一条 | 单 agent | 还是一条，只是没人看着 |
| **老板派活给干活的，干完回传** | **多 agent** | 有归属、有任务、有回流 |

**「多会话」不等于「多 agent」。** 单 agent 阶段可以有很多条会话。

### 边界二 · 工程上跨没跨线

**单 agent 全程只消费 pi 已经在发的事件、已经导出的函数。**
**多 agent 的第一刀开始向 pi 注册新能力。**

```bash
grep -rn "registerTool" src/     # 0 个调用点 = 还在单 agent 侧（当前实测：0）
```

**实现落点三层，优先级 3 > 2 > 1，往上走一级要在 PR 里写理由：**

| 层 | 是什么 | 参照 |
|---|---|---|
| 3 | ORBITA 自己的代码 | 默认落点。全表约 80 刀里 77 刀在这层 |
| 2 | pi 扩展（注册工具 / 挂事件钩子） | 全表只有 3 刀 |
| 1 | 给 pi 打补丁 | 目前看不到必须用的地方。Proma 六个月全部补丁 22 行 |

## 二、排序按什么排（本文档的核心）

十个批次的顺序不是拍脑袋，是五条依据的合成。**每条依据单独看都有道理，它们之间会打架**——打架的地方在第四节列出来供拍板。

### 依据 A · 硬依赖：不做完这个，那个物理上做不了

最强的一条，没有商量余地。

```text
工具结果这条链  →  委派结果才有地方放
干活的 agent    →  才有东西可检查
质检的分        →  审计员才有东西可算
两种以上模式    →  "再加第三种"才有意义
```

### 依据 B · 反馈速度：早点让它真的跑起来

**批次 2 只有 5 刀，是所有批次里最小的，这是故意的。**
在"两个 agent 真的协作完成一件事"发生之前，后面所有设计都是纸上的。
让这件事尽早发生一次，比把它设计得更完整重要。

### 依据 C · 改动成本随时间上升：现在便宜，以后贵

有些东西**不是"早晚都一样"**：

| 东西 | 现在的成本 | 晚了的成本 |
|---|---|---|
| `visibility` 字段 | 加 1 个字段 | 回填全部历史会话文件才能判断旧记录该不该显示 |
| 会话回收 | 加一个方法 | 从"开 20 条漏 20 条"变成"每次派活都漏" |
| 接口形状 | 想清楚一次 | 每个消费者都要改 |

**但这条依据只决定「早点做」，不能用来正当化「做一批看不见的东西」。**
批次 0 里的两件事——工具结果看得见、内部消息不污染对话——**本身就是用户要的功能**，
它们顺便才是多 agent 的前置。第一版我把它们包装成"地基准备"，反而让它们失去了功能面目，那是错的。

### 依据 D · 价值随规模才显现：现在做是浪费

反过来的一条：

| 东西 | 为什么现在做是浪费 |
|---|---|
| 门房（省老板的上下文） | 子 agent 只有 2 个时，省不下什么，还多一次模型往返 |
| 真事件总线（通配订阅） | 少于 4 个子 agent 时，逐个装钩子和订阅总线没有可观察差别 |
| 五道通信守卫 | 只有一种协调模式时，后四道无对象可守 |
| 多用户全套 | 单用户下这些字段退化成空值 |

**这条依据不是"不做"，是"等它有消费者"。** 触发条件见第五节。

### 依据 E · 外部经验强度：有人做过的，风险低

架构文档里有一份 47 篇论文的对照（**注意：该文档自称 AI 生成，论文清单链接是空的，只能当弱信号**）：

```text
多规划者协商（规划员）      8 篇论文做过
多方案选优（竞功）          8 篇
隔离工作区并行              7 篇
事后审计                    5 篇
表现记分册反馈              5 篇
────────────────────────────────
质检班子那一套              0 篇  ← "论文生态盲区"
```

**0 篇 = 没人做过 = 没有经验可参考。** 第一版我把它读反了，当成"唯一有依据"。

正确用法：**有依据的先做，风险低；没依据的也要做，但要留出踩坑的时间。**

## 三、十个批次，以及每个批次为什么在这里

| 批次 | 做什么 | 刀数 | 排在这里因为 |
|---|---|---|---|
| **0** | 让 agent 干的事看得见、留得住 | 4 | **依据 C**：工具结果记录与 `visibility` 字段越晚做越贵。**但它们本身就是用户要的功能**，不是为后面做的准备 |
| **1** | 单 agent 深化 | 15 | 无硬依赖，**可与批次 2 并行**。pi 已把原语给全，成本在界面不在内核 |
| **2** | 老板 + 干活的（最小闭环） | 5 | **依据 B**。全表最小的一批，故意的——尽快让"两个 agent 协作"真的发生一次 |
| **3** | 规划员 + 并行串联 | 8 | **依据 E**（规划员 8 篇论文）+ **依据 A**（并行要先有单个派活跑通） |
| **4** | 质检班子 + 记分册 + 审计员 | 10 | **依据 A**：没有干活的就没有可检的；审计员算的是质检的分。**依据 E 是负的**（0 篇），要留踩坑时间 |
| **5** | 复核员 + 门房 | 6 | **依据 D**：门房的价值随子 agent 数量增长，前面几批数量还不够 |
| **6** | 多方案选优（隔离工作树） | 4 | **依据 E 最强**（8 篇 + 7 篇），但**最贵**——要先做隔离工作树。两条依据打架，见第四节 |
| **7** | 编排模式扩展 | 8-10 | **依据 A**：要先有 2-3 种模式共存，"再加一种"才有意义 |
| **8** | 基础设施从最笨升级到终局 | 10-12 | **依据 D**。见下方说明 |
| **9** | 多用户 | 8-10 | **依据 D**：等产品决定支持多用户 |

**合计约 78-84 刀。**（批次 0 从横切的 11 刀改成纵切的 4 刀，见第六节分刀原则。）

### 批次 8 的存在方式（最容易误解的一条）

批次 8 里的东西**不是"到那时才出现"**，而是：

```text
前面批次    以最笨形态出现，接口按终局形状一次定好
批次 8      换实现，接口不动
```

这是架构文档的原话：「Phase 1 简化为可变对象 + activityLog，**接口按终局形态设计，后续升级换实现不改接口**」，那一段的小标题就叫「接口稳定」。

| 东西 | 前面批次的最笨形态 | 批次 8 换成 |
|---|---|---|
| 消息总线 | 直接函数调用 | 通配订阅 + 三条通道分优先级（防紧急被日常淹没） |
| 状态 | 我们的 JSONL | 命名空间分区 + 按分区投影 |
| 请求上下文 | 只带一个 traceId | 完整字段（文档策略是"只加不改"，是并集不是二选一） |
| 通信守卫 | 一个能力判断 | 五道 |
| 记分册 | 批次 4 的 JSON | 带衰减、带防过早收敛 |

**代价要说清楚**：这个做法要求前面每一批都多花时间在接口设计上。这是第四节待拍板的第三条。

## 四、依据打架的地方（待拍板）

### 岔口 1 · 多方案选优该不该提前

- **依据 E 说提前**：8 篇 + 7 篇论文，全表外部经验最强的一块
- **依据 A 说不能提前太多**：要先有隔离工作树，那是全表最贵的一块
- **依据 B 说不急**：批次 2 已经让"多 agent"跑起来了，不缺这个证明

现在排批次 6。**要不要提到批次 4（质检）之前？**
提前的好处是先走成熟路线；代价是把最贵的一块提到前面，质检往后推。

### 岔口 2 · 质检班子 0 篇论文，怎么定位

它是架构文档着墨最多的部分，也是**没人做过**的部分。

- **当差异化主攻**：没人做过 = 机会。但没人趟过坑，要留返工预算
- **当正常一批**：按依据 A 排在有干活的之后，不给特殊地位

第一版我给了它特殊地位，理由是引错的。**现在按依据 A 正常排在批次 4，没有额外加权。** 你要不要加？

### 岔口 3 · "接口一次定好"接受为通用原则吗

接受：前面每批多花时间在接口设计上，换批次 8 只换实现不改调用点。
不接受：批次 8 变成一次大改，每个消费者都要动。

## 五、现在不做的东西，什么时候做

第一版有一节叫「明确不做」，**框架是错的**——架构文档里的东西全都要做，只是排序。改成触发条件：

| 东西 | 触发条件 |
|---|---|
| 真事件总线 | 批次 8；或**子 agent 并发上到 8 个**时提前 |
| 状态命名空间分区 | 批次 8；或出现"多个 agent 读写同一份状态"的需求时提前 |
| 请求上下文完整字段 | 批次 8，字段按需追加（文档策略就是"只加不改"） |
| 五道通信守卫 | 批次 8；或第二种协调模式落地时提前 |
| 同辈网状 / 联邦 | 批次 7，需先有 2-3 种模式共存 |
| 混编模式 | 批次 7 末，前置是层级模式和竞争模式都已落地 |
| 多用户全套 | 批次 9，等产品决定支持多用户 |
| 可视化编排画板 | 未排期。旧分支做过一版，实际只能表达"8 个角色的开关"，不是真编排 |

## 六、纪律

**0. 批次 ≠ PR。** 批次是一组相关功能；**一刀 ≈ 一个 PR**。

**1. 按功能纵切分刀，不按技术层横切。**
一个功能从事件采集到界面显示要穿过 4 个文件，**那是它的自然范围，不叫大重构**；
硬拆成「采集 / 落盘 / 导出 / 渲染」四刀，前三刀就没有意义了。
**大刀的定义是「一次改很多不相干的东西」，不是「改了几个文件」。**

**2. 一刀 = 一个可演示的行为变化 + 它的测试 + 一个真实调用点。**
看不出变化的刀只有两种合法形态：
① 协议前置 PR（小，与实现同批合并，因为项目规则要求 `src/shared/` 单独成 PR）；
② **诚实标注为工程债的刀**（内存修复、补回归测试）——**不要把债装成功能**。
纯判定逻辑尤其要守——它最容易变成写得爽、测得爽、永远接不上的死代码。

**3. 每一刀必须写清楚"不要顺手做什么"。** 这是防止范围膨胀的机制本身。

**4. 纯判定逻辑的文件不许 import pi，接线文件不许写判定逻辑。** 一个 grep 就能守住。

**5. 往层 2 或层 1 走，在 PR 描述里写理由。**

**6. 判定逻辑什么时候提成包**：出现第二个真实调用方（测试不算），且跨越进程或应用边界。按本表，批次 0-7 全程不触发。

## 七、第一版错在哪（一轮对抗性核查的结论）

核查方法：把计划里 15 条对架构文档的引用逐条追回原文。
**结果：对 pi 的判断全部一手实测、全部通过；对架构文档的引用 6 处失真，形态高度一致——引文对、范围丢、结论倒。**

| 我说的 | 原文其实是 |
|---|---|
| 质检班子是「唯一有外部论证的原创点」 | 那一栏标题是「**论文生态盲区**」，三项论文数**均为 0**。0 篇 = 没人做过。**方向反了** |
| 大明模式 0 篇论文所以不做 | 同一个"0 篇"，我对质检读成"主攻"、对大明读成"不做"。同一规则得相反结论 → 这条规则不能承重 |
| 状态层"Phase 1 就是可变对象，根本没有事件溯源" | 后半句是「接口按终局形态设计，后续升级换实现不改接口」，小标题叫「**接口稳定**」。文档从没说不做 |
| 记分册要等竞功才有分可记 | 文档明写「不只竞争模式用，层级模式也用」 |
| 我们规矩禁数据库所以不做记分册 | 数据库是后期形态，**第一版本来就是空壳不落盘**——我反对的是自己不会建的那个版本 |
| 门房的"全程协调"已由"显示花费"替代 | 原文是「持续**压缩**中间结果」。显示花费是只读数字，不压缩任何东西 |

另外**漏了两个一级角色**：规划员、审计员。不是考虑后否决，是没进视野。已补进批次 3 和批次 4。

**第二版还错了一件事**（wafo 2026-08-30 指出）：批次 0 按技术层横切成 10 刀，其中 7 刀看不出变化，
**违反了本文档自己第六节第 2 条**。已改为按功能纵切的 4 刀。

**三处架构文档自身的矛盾**，记在这里供后续裁决：
派活预算有**三份**互不相同的定义（不是两份）· 第一版允许派几层有两说 · 复核员归属哪个阶段有两说。
