# C-4 · 会话内可换模型

> 批次计划：`2026-08-30-批次1-单agent深化.md` C-4。
> 演示：对话进行中换一个模型，下一轮用新模型，**会话不断**。

## 已定的决定（2026-09-02 与用户对齐）

1. **就地切换，不再开新任务**。此前 `chooseModel` 会 `reset()` 掉当前会话引用，
   理由是「界面上写的和实际在跑的对不上」——这个顾虑解除：pi 的切换语义本身就是
   安全的（见下），reset 反而把人踢出正在看的会话。
2. **跑动中不禁用**。正在回答 / 工具在跑时菜单照常可用。分支按钮禁用是因为
   「工具结果没齐时裁出去的上下文是畸形的」；换模型没有对等风险——
   「这轮答得不行，换个模型接着问」正是本功能最真实的场景。
3. **新任务默认跟着变**。renderer 只有一份 `model` state（会话意图 + 新任务默认），
   切换成功后经事件更新它——不拆两份状态。
4. **接受非活会话的落空损耗**。打开盘上历史、agent 里没活会话时，切模型只改
   renderer 意图，下一条消息 create(resume) 时才生效；换了却不发言就切走，
   会被 openSession 的 meta 播种冲掉（等于没换过）。零额外代码，语义是
   「换模型跟着一条消息才作数」。
5. **不写用户的全局 pi 设置**。锁定版 pi 的 `setModel(model, {persist})` 默认
   `persist: false`（session-only）——不传 persist 就不会碰 `~/.pi/agent/settings.json`。
   （pi TUI 的切换默认写全局默认；我们不要这个跨应用副作用。）

## 机制（pi 侧事实，核实过锁定版源码）

`session.setModel(model)`（agent-session.js:1201）依序做：

1. `checkAuth`——provider 没配 key 抛 `No API key for ...`
2. 改 `agent.state.model`——**对正在跑的轮无效**：loop config 在 run 启动时快照了
   model，本轮（含工具循环、插队消息）全用旧模型；**下一次 `prompt()` 起新模型**。
   排队消息本轮结束后投递 = 新一轮 = 新模型，与「下一轮生效」天然一致。
3. `sessionManager.appendModelChange`——落一条 `model_change` 进 pi 自己的本子
4. `setThinkingLevel` clamp——新模型不支持 thinking 就降档；我们 UI 不暴露
   thinking，全自动，不用管
5. resume 恢复语义已核实（sdk.js:87）：`if (!model && hasExistingSession && ...)`——
   **显式传入的 model 永远赢**。我们的 resume 永远传 renderer state（从 meta 播种），
   所以 meta 是 resume 模型的真值，pi 本子里的 model_change 只是兜底。

pi 已内建、我们不用做的：旧模型的上下文溢出不会触发新模型的自动压缩（sameModel
守卫）；标题生成读 `live.session.model` 自动跟随新模型。

## 数据流

```
renderer 菜单点选
  ├─ sessionRef.current !== null（活会话）
  │    └─ api.agent.setModel(sessionId, providerId, modelId)        [第3层]
  │         └─ main handler：ProviderStore resolve 完整 provider      [第2层]
  │              （unknown provider / 无 key → invoke reject → 红字）
  │              └─ host.setModel → runtime
  │                   └─ registerAndResolveModel（复用 create 的注册解析）
  │                        └─ live.session.setModel(model)
  │                             ├─ 失败 → failed 事件（操作级红字）
  │                             └─ 成功 → {type:"model"} 事件
  │                                  ├─ recorder 落 meta（providerId/modelId）
  │                                  └─ renderer：对齐 model state（Q3 默认跟随）
  │                                     + refreshSessions
  └─ sessionRef.current === null（首页 / 盘上打开未唤醒）
       └─ 只 setModel state——下一条消息 create 时生效（决定 4）
```

**事件驱动、不乐观**（与 changeMode 的乐观更新不同，理由：setModel 会失败——
无 key、未知模型。乐观更新会把 chip 写到实际没切过去的位置，正是本刀要消灭的
「写的和跑的对不上」）。失败路径：main 侧装配失败走 invoke reject，runtime 侧
走 failed 事件，都进现有的红字提示；chip 与 meta 不动。

## 被否决的方案

- **翻译 pi 的 `model_select` 事件当回执**——切换是我们自己发起的，成功后直接发
  orbita 的 `model` 事件即可；订阅翻译层是为「不是我们发起的变化」准备的，这里没有
  那种来源（resume 恢复发生在 create 时，meta 本来就是对齐的）。
- **乐观更新 state**——见上，失败时 chip 与实际跑的模型脱节。
- **非活会话也走 main 立刻落 meta**——要多一条 session 域 IPC，服务的只是一个
  「换了模型却不发消息」的边角，决定 4 接受损耗。
- **拆两份状态（会话模型 / 新任务默认）**——决定 3，一份 state。
- **跑动中禁用菜单**——决定 2。
- **pi 的 `cycleModel` / Ctrl+P 循环、`/model` 命令**——菜单点选已覆盖需求，
  循环切换是 TUI 键位交互，DOM 菜单没有它的位置。

## 不做什么

- 消息旁标注「这条是哪个模型答的」（协议 assistant item 已有 model 字段，渲染是另一刀）
- 暴露 thinking level
- pi 内建目录模型进菜单（候选仍 = 用户 provider 的声明模型）
- 对话流里插「已切换到 X」的系统行——chip 与下一轮回答就是反馈
- 新任务默认持久化（refresh 后仍从第一个 provider 播种，与现状一致）
