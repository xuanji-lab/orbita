## 2. 明朝架构（文官体制）摘要

### 2.1 来源与核心思想

来源：`ming-frameworks/ming-architecture.md`

核心思想：**权力制衡**。用户请求经翻译进入系统后，由总控最终裁决，内阁多名规划 Agent 协商出方案并由首辅加权裁决，六部执行层各司其职，三层独立监察确保合规与质量。暂停权与恢复权分离，紧急通道允许总控在规划层失效时直接向执行层下发预设降级方案。

### 2.2 六层架构概述

| 层次 | 明朝映射 | 核心职责 |
|------|----------|----------|
| 交互层 | 司礼监 | 翻译用户输入为内部指令（批红），审查规划输出，控制交互节奏 |
| 决策层 | 皇帝 | 最高决策权，汇总结果，紧急通道降级 |
| 规划层 | 内阁 | 多名规划 Agent 各自出方案，首辅加权裁决 |
| 执行层 | 六部 | 各负责特定领域，互不干扰 |
| 监察与复核层 | 六科/都察院/大理寺 | 过程监控、事后审计、高风险复核 |
| 通信层 | 六部公文往来 | 订阅-发布总线，授权列表 + 日志审计 |

### 2.4 决策摘要

**决策 1：多规划者协商 vs 单点规划**

**选择**：多名规划 Agent 独立出方案，首辅加权裁决。

**理由**：单点规划在复杂任务中容易遗漏关键子任务。多规划者提供视角多样性，首辅加权综合各方优势。

**影响**：规划层变为多 Agent 协作形态，引入置信度标签和加权裁决逻辑。

---

**决策 2：三层监督分离设计**

**选择**：监督拆分为过程监控（六科给事中）、事后审计（都察院）、高风险复核（大理寺）三个独立角色。

**理由**：单一监察角色同时掌握过程控制、结果评价、最终裁决三种权力，容易形成监察垄断。

**影响**：监察层从单体变为三元组，接口设计需支持三种不同强制力等级。

---

**决策 3：暂停权与恢复权分离**

**选择**：监督 Agent 仅拥有暂停权，无恢复权；恢复权由总控和首席规划 Agent 共享。

**理由**：同一 Agent 同时掌握暂停和恢复权力，可能滥用暂停作为控制手段。

**影响**：监督 Agent 接口中不包含恢复方法，恢复逻辑转移到总控和首辅。

---

**决策 4：紧急通道降级机制**

**选择**：总控拥有紧急通道，在规划层超时或冲突无法解决时，可直接向执行层下发预设降级方案。

**理由**：规划层作为中间环节存在失效风险（超时、死锁、方案冲突）。预设降级方案保证降级输出可预期。

**影响**：总控接口新增 `emergencyFallback` 方法，执行层需要能够接收并执行降级方案。

---

**决策 5：协作总线订阅-发布模式**

**选择**：执行层 Agent 之间通过订阅-发布模式的协作总线间接通信，总控维护授权订阅列表并对消息日志审计。

**理由**：直接点对点通信会导致执行 Agent 之间强耦合，新增 Agent 或调整领域都需要修改多个通信链路。

**影响**：执行层 Agent 不再直接引用彼此接口，总控新增授权管理和日志审计职责。

---

### 2.5 与 v4 内阁制的关系

v4 内阁制（`12-chaoting-mode.md`）将明朝架构升级为 **hierarchy Preset**：
- 六层架构映射为 v4 核心微内核 + 执行层 + 监察层 + 通信层
- 文官术语（总控、首辅、六部、都察院等）作为内阁制的独立术语体系，与竞功制术语严格不交叉
- 司礼监（交互审核 Agent）升级为前置关口 + 代批机制（`15-sijian-batch.md`）
- 军功簿（WeightRegistry）和事件溯源状态（EventSourcedState）作为 v4 通用基础设施，不专属于内阁制

## 3. 竞功制（军事体制）摘要

### 3.1 来源与核心思想

来源：`ming-frameworks/jinggong-system.md`

核心思想：**以功定赏**。同一任务复制多份并行分发给各路提督 Agent，通过预设功赏指标择优或融合方案，最终挂载回主分支。各路独立攻关，不横向通信，评功推官按维度评分后择优，军功勘验使事后复盘并影响后续调用权重，形成迭代反馈闭环。

### 3.2 七层架构概述

| 层次 | 明朝映射 | 核心职责 |
|------|----------|----------|
| 交互层 | 军情转译使 | 翻译用户请求为军令，保留原始战报，审查最终战果 |
| 决策层 | 总督 Agent | 复制任务副本，分发各路，维护 worktree，最高裁决权 |
| 并行执行层 | 各路提督 Agent | 独立接收同一任务副本，采用不同战术或路径解决问题 |
| 融合决策层 | 评功推官 | 按功赏指标择优或融合，挂载回主分支 |
| 监察层 | 监军御史 Agent | 实时监控资源消耗、超时及违规，暂停单路（挂白旗） |
| 事后审计层 | 军功勘验使 | 事后复盘，给出评分和修正建议，影响后续调用权重 |
| 通信层 | 塘报旗牌使 | 点对多号令分发，固定频道独立上报，接收清单防遗漏 |

### 3.4 决策摘要

**决策 1：worktree 并行分支 vs 单分支重试**

**选择**：多 worktree 并行分支，各路提督独立执行，不重试单一路径。

**理由**：并行分支用空间换确定性，不同战术路径同时探索，大幅提高找到全局优质解的概率。

**影响**：增加基础设施复杂度（worktree 管理、通信协议），但任务完成率和方案质量显著提升。

---

**决策 2：择优 vs 融合策略**

**选择**：评功推官同时支持 best（择优）和 merge（融合）两种策略，由任务配置决定。

**理由**：不同任务适合不同策略。简单任务有明显最优解，best 足够；复杂任务各路各有所长，merge 能产生超越任何单路的合进方案。

**影响**：评功推官接口需同时支持 select 和 merge 两种模式。

---

**决策 3：事后审计影响后续调用权重**

**选择**：军功勘验使的评分结果调整各路提督的后续调用权重，形成迭代反馈闭环。

**理由**：静态竞争只解决单次任务最优，动态权重让系统在多次任务中持续进化。表现稳定的提督获得更多任务机会。

**影响**：权重调整算法需要防止过早收敛，权重持久化是必选项。

---

**决策 4：各路禁止横向通信**

**选择**：严格禁止各路提督 Agent 之间的横向通信，仅通过总督和评功推官间接交互。

**理由**：横向通信会破坏竞争公平性。如果各路可以协商或交换信息，评分就失去了独立比较的意义。

**影响**：每路必须产出完整可独立评估的结果，不能依赖其他路的产出补全。

---

**决策 5：接收清单防篡改机制**

**选择**：塘报旗牌使维护分发记录和回报记录，总督 `confirmAllReported` 必须验证两者一致后才启动融合。

**理由**：并行环境下可能出现消息丢失、重复或篡改。接收清单确保总督知道哪些分支已分发、哪些已回报。

**影响**：融合启动条件从"收到任意结果"变为"收到全部预期结果"，增加了等待成本，但大幅降低错误融合概率。

---

### 3.5 与 v4 竞功制的关系

v4 竞功制（`13-jinggong-mode.md`）将竞功制升级为 **market Preset**：
- 七层架构映射为 v4 核心微内核 + 交互层 + 并行执行层 + 融合决策层 + 监察层 + 审计层 + 通信层
- 军事术语（总督、提督、评功推官、军功勘验使等）作为竞功制的独立术语体系，与内阁制术语严格不交叉
- worktree 分支管理升级为 v4 通用隔离机制（任务级/并行级隔离）
- 军功簿（WeightRegistry）作为 v4 通用基础设施，支持竞功制的迭代权重反馈

## 5. v4 升级要点

### 5.1 从独立框架到 璇玑 Preset

两套参考框架原本是独立的多 Agent 协作设计。v4 将它们升级为可插拔的 **Coordination Pattern Preset**：
- 内阁制 → hierarchy Preset（层级协商模式）
- 竞功制 → market Preset（并行竞争模式）

Preset 是 v4 Pattern 体系的一等公民，可注册、可切换、可组合。

### 5.2 术语体系不交叉规则

v4 两套协作模式各自拥有独立术语体系，严格不混用：
- 内阁制术语（总控、首辅、六部、都察院...）仅用于内阁制文档和实现
- 竞功制术语（总督、提督、评功推官、军功勘验使...）仅用于竞功制文档和实现
- 同一职能在两模式下有不同名字，写文档时只出现本模式术语，共享能力用核心通用名

见 `21-*` 原则（两模式不交叉规则）。

### 5.3 与微内核 / Pack / 四库的对接

| 核心概念 | 对接方式 |
|----------|----------|
| Agent | 两模式均使用 v4 Agent（由 Identity 定义），不硬编码角色枚举 |
| Loop | 四库中的 Loop 库提供可插拔执行引擎，两模式共享 |
| Communication | 图状通信（点对点 + 发布订阅 + 频道）替换原有总线模型 |
| State | 事件溯源共享状态 + 命名空间替换原有对象状态 |
| Pattern | Coordination × Execution 两层 Pattern 容纳两模式 |
| Domain Pack | 领域能力通过 Pack 可插拔，两模式均不内置领域逻辑 |

四库（身份库、架构提示词库、技能库、Loop 库）为两模式提供统一的资产管理体系。模式文档只定义 Pattern 层的 Coordination 和 Execution 契约，不直接引用领域资产。
